1. **Every Analysis Services processing call fails on Windows** (`ProcessPartitions`, `ProcessTables`, `ProcessModel`, `Recalculate`, `EnsurePartition`, `RemovePartition`). §G. Repro: `AnalysisServices.Connect("<ssas>", "<model>").ProcessPartitions(new[] { ("DimProduct", "DimProduct") })` with the released 0.14.0 kernel → `TypeLoadException: Could not load type 'Microsoft.AnalysisServices.Utilities.WindowsDesktopAssemblyResolver' from assembly 'Microsoft.AnalysisServices.Runtime.Windows, Version=19.114.8.0'`. Cause: TOM from `Microsoft.AnalysisServices.NetCore.retail.amd64` 19.84.1 paired with `AdomdClient` 19.114.8. The failing type is only loaded on the Windows branch of TOM's identity resolver; the same package pairing ships everywhere, and TOM was not tested on macOS/Linux. **Fix: `windows/ssas-tom-package` `068dc11`** (package → `Microsoft.AnalysisServices` 19.114.8, plus a server-less regression test; verified processing on the real SSAS).
2. **A secret a cell throws with is written unredacted to logs, including Studio's `run.log` on disk.** §Q, §O. Repro: a Studio job cell `throw new Exception("x=" + Environment.GetEnvironmentVariable("CLRKERNEL_SECRET_…"))` → `run.log` line `kernel: System.Exception: x=<value>` (served by `GET /api/runs/{id}/log`). The same happens on `clrkernel run` stderr (CI logs) and `clrkernel lsp` stderr (the VS Code output channel). Artifacts, replies and notifications were masked. Not Windows-specific. **Fix: `windows/redact-logged-exceptions` `d0bfd2e`** (the four fronts log `SecretRedaction.Redact(e.ToString())`; the masking test now captures the log).
3. **The ODBC opt-in provider cannot open any connection when loaded with `#r "nuget:"`.** §F. Repro: `connections.json` `"$type": "Odbc"` + `#r "nuget: ClrKernel.Database.Provider.Odbc, 0.14.0"` + `-- connections <name>` → `FileNotFoundException: System.Data.Odbc, Version=9.0.0.0`. Cause: the kernel carries System.Data.Odbc 8.0.0.1 (PowerShell SDK → Microsoft.Windows.Compatibility), and the provider was compiled against 9.0.0. The kernel's deps are the same on every OS, so this is very likely not Windows-specific; only verified here. **Fix: `windows/odbc-provider-version` `0981974`** (8.0.1, plus a test comparing the provider's and the kernel's restore graphs; A/B verified against SQL Server through ODBC Driver 18).
4. **Saving a `.dib` in VS Code corrupts directive lines** (silent data loss). §K. Repro: a `#!sql` section whose first line is `#!sql-connect --name …`, or a `#!value` section starting `#!value --name …`. After a save they read `-connect --name …` and `--name …`. Cause: `writeDib` strips a repeated selector by prefix, without an end-of-line anchor. Not Windows-specific. **Fix: `windows/dib-directive-prefix` `d6bc859`** (anchored + escaped, plus a test; 89/89 extension tests).
5. **Python is never provisioned on a stock Windows machine.** §L. Repro (on a machine that has never provisioned: delete `%LOCALAPPDATA%\clrkernel\python` first, because a provisioned interpreter is preferred over PATH, and this VM is now provisioned): no real Python on PATH, but `%LOCALAPPDATA%\Microsoft\WindowsApps` on PATH (Windows 11's default App Execution Alias `python.exe`, a 0-byte reparse point). The first `#!python` cell fails: `Python at '…\WindowsApps\python.exe' did not start as a notebook interpreter — it exited immediately.` `PythonInterpreter.OnPath()` accepts the alias because `File.Exists` is true. Without the alias, provisioning works (uv 0.12.9 + CPython 3.13.15, 24.9 s; pandas 13.9 s). Windows-only. **Reported, no branch**: the right behaviour (skip WindowsApps aliases, or fall back to provisioning when the PATH interpreter will not start) is a design choice.
6. **Git Bash: a `cd` in one cell is lost by the next.** §L. Repro: with Git Bash on PATH, run `cd` to any Windows directory, then `pwd` in the next cell → back in the notebook folder. `ShellTest.Working_directory_persists_across_cells` fails (`actual: "/c/src/…"`). Cause: MSYS `pwd` output (`/c/…`) rejected by `Directory.Exists`. Windows-only. **Fix: `windows/git-bash-cwd` `bf7b45d`** (`cygpath -w "$PWD"` with a `pwd` fallback; ShellTest 22 passed, 1 skipped for zsh).
7. **Studio Connections: a non-SqlServer connection that needs no password cannot be tested or queried.** §O. Repro: save an Odbc connection with `connectionString` `…;Trusted_Connection=yes;…` and no password, then `POST /api/connections/{id}/test` → `No secret found for 'clrkernel-studio:conn:<id>'. Looked in: memory, credential-manager, env.` Cause: every saved connection gets a default `SecretRef`, `QueryRunner.NodeFor` always passes it as `password`, and `ConnectionConfig.From` resolves it eagerly. Not Windows-specific. **Reported, no branch** (whether the default reference should be optional is a design decision).
8. **VS Code (`lsp`) cannot see a second notebook's own non-SqlServer `connections.json` entries.** §F. Repro: one `clrkernel lsp` process (cwd = the first notebook's folder), then a notebook in another folder with `"$type": "Odbc"` in its own `connections.json` → `No SQL connection named 'viaodbc'.` Cause: `SqlTarget.ProviderTypesInConfig()` and `ConnectionConfig.Load(name, …)` default to `Directory.GetCurrentDirectory()`. Not Windows-specific. **Reported, no branch** (the session needs the notebook directory plumbed through).
9. **The Studio browser suite cannot run on Windows.** §O. `build.sh` (WinError 193), `os.killpg`, `Meta+A` select-all (the Windows key on Windows), and a fixed 4 s completion wait that is too short on this VM. Windows-only (test infrastructure). **Fix: `windows/studio-harness` `fa24def`** (18/18 checks pass on Windows).
10. **`#!sql-connect --provider Odbc` is accepted, advertised and ignored.** §F. The connect cell reports `Connected`, then the first query fails inside SqlClient with `Keyword not supported: 'driver'.` Completion describes `--provider` as "ADO.NET provider override"; `SqlConnectionSpec.Provider` says only "sqlserver" is supported. **Reported**: refuse non-sqlserver values at connect time, or drop the flag from completion.
11. **`PRINT` and informational messages never reach a notebook SQL cell.** §F. `PRINT 'x'` → badge `OK`, no text anywhere; nothing subscribes to `InfoMessage`. A spec expectation the product does not implement (Studio's query console does). **Reported.**
12. **`#!sql-deploy --dry-run` reports `0 definition file(s) planned.` under a board listing the planned files.** §F. **Fix: `windows/sql-deploy-dryrun-count` `08a306e`** (plus a test).
13. **Web app `noLiterals.test.ts` fails on every Windows checkout** (backslash paths versus a `/` allow-list). §A. Test-only, Windows-only. **Fix: `windows/webapp-nolit-paths` `b0b0798`** (542/542).
14. **`build.ps1 Test` intermittently fails in its Build target with `MSB3713 … AssemblyInfo.cs … being used by another process`.** §A. Reproduced twice, while reused MSBuild nodes from earlier builds were alive; then `build.ps1 Build` ×2 and `build.ps1 Test` ×1 passed. The plain `dotnet build` of the same solution never failed, including `--no-incremental`. Windows file locking; not deterministic, and the cause was not isolated (it was not shown that Nuke itself differs from `dotnet build`). **Reported, no branch.**

### Where the spec does not match the product (not bugs)
- §B filter names are file names; `SqlEtlTest`, `SqlPhase2bTest`, `FluentSqlTest`, `MultiProviderTest` match no class. With `REQUIRE_LIVE=1` the filter also includes `RunStoreContractTest ("postgres")`, which must fail without Docker.
- §F `#!ansisql` does not run on a SqlServer connection by design (Postgres/Odbc/Jdbc). `--provider Odbc` on `#!sql-connect` is not a supported way to use ODBC. Live-schema table/column completion is Studio's, not VS Code's.
- §L `winget install Git.Git` puts only `Git\cmd` on PATH, not `bash`.
- §P `-p name=value` is `-p NAME VALUE`.
- §1 Node 24.15.0 was on the VM rather than 20 LTS; everything passed on it.
- §A "Skipped should be the live-gated tests only": 12 skips are Windows platform inconclusives (9 bash, Unix file modes, symlink privilege, chmod).

(2) The `--user`/`--secret` path is unverified: the stored password was wrong during this run (since corrected on the VM), so it needs one re-run.
- Python finding 5: skip the WindowsApps alias, or treat "exited immediately" as "no interpreter" and provision?
- Studio finding 7: should the default `SecretRef` be optional when no secret is configured, or should the Odbc/Postgres/… forms say "password optional" explicitly?
- The Jupyter front's redaction change (finding 2) compiled and is covered by the shared pattern, but was not driven end-to-end through Jupyter.
- `NotebookTree`'s symlink-escape guard and `ProjectRegistry`'s unwritable-folder message have no Windows test (both inconclusive here: no symlink privilege, no chmod).
